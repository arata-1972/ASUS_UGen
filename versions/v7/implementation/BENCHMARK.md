# Measured integration evidence


A minimal authorized test used our own synthetic Mandarin narration WAV, then the Taiwanese WAV generated by our own TTS. No customer recordings or billing gateway was used. These are one-sample integration measurements, not a recognition accuracy evaluation. Recognized text contains errors and those errors propagated through translation. Useful reception conversations still require original/translation review and separate real-speaker evaluation.

| Direction / stage | Client elapsed time | Evidence |
|---|---:|---|
| Mandarin → Taiwanese: ASR | 29,848.82 ms | `evidence/zh_to_tw/recovered_audio.json` |
| Mandarin → Taiwanese: EOLE | 178.53 ms | same |
| Taiwanese TTS generation | Not recorded; HTTP 200 | same |
| Previously generated Taiwanese audio download | 2,533.11 ms | same |
| Generated Taiwanese audio → Mandarin: ASR | 2,427.29 ms | `evidence/benchmark_reverse.json` |
| Reverse EOLE | 750.91 ms | same |
| Mandarin TTS | 3,883.90 ms | same |
| Reverse complete run | 7,069.29 ms | same |

The first forward run stopped with `TTS_AUDIO_ORIGIN`: the service returned a hosted audio origin that had not been configured. This was an explicit safety failure, not a successful full pipeline. After configuring the known returned hosting origin, we downloaded that already generated asset without regenerating TTS. `recovered_audio.json` records this recovery; it does not invent a missing TTS generation time. The reverse input SHA-256 equals the recovered Taiwanese output SHA-256 (`5ee5ce787b8f76783e4f66fd7ac39e79cb3622a701002ed7f39725aad71dd4bd`). The reverse run completed the actual ASR → translation → Mandarin TTS pipeline.

The reverse client was Node v20.18.0, macOS arm64, Apple M5, 32 GiB RAM. Recorded client RSS was 93,945,856 bytes at report time. This is the bridge process, not server/model memory. All times include HTTP/network overhead. No warm-up, repeated distribution, concurrent throughput, GPU utilization, accelerator memory, or ASUS hardware inference was measured. Local missing-model/configuration and unimplemented-hardware errors in `evidence/local_errors.json` are failure handling evidence, not inference performance.

Generated WAVs: `evidence/zh_to_tw/output.wav` and `evidence/tw_to_zh/output.wav`. Raw stage output is retained, including erroneous recognition, rather than replaced with an expected answer. `npm test` separately validates adapter contracts and failures using fixtures; its passes do not imply model quality. The local browser server starts on loopback independently of inference.

## Additional reception UI test

A separate actual browser run used a new Taiwanese synthetic question, generated by EOLE from “請問服務台在哪裡？” and our Taiwanese TTS. The generated input sentence was “請問服務台佇佗位?”. Actual ASR returned the erroneous “請問服務代到位去。” in 803.00 ms. The operator replaced it with the known source question “請問服務台佇佗位？”. EOLE then returned “請問服務台在哪裡?” in 189.36 ms. The operator normalized punctuation before actual Mandarin TTS (1,146.74 ms server elapsed; 1,164.10 ms browser elapsed). The browser audio control visibly entered the playing state. These values differ from the earlier CLI run and must not be combined. Download link availability was visible; automated blob download verification was unsupported. Evidence is in `evidence/reception_demo/`. Recognition accuracy was not passed; the correction is explicit.
